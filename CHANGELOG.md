## [v2.1.0] - 2026-08-01

### Added

- Added REST endpoints for Machine BMC reset, DPU reprovisioning, and health report override management, proxying authorized Provider Admin requests through the NICo Core gRPC proxy to the machine's owning Site. BMC reset supports an optional ipmitool reset selection; DPU reprovisioning accepts Set, Clear, or Restart modes with an optional firmware update; and health override endpoints support listing, inserting, and removing overrides. See https://nvidia.github.io/infra-controller/ for the updated schema. (#2849)
- Added HostInband as a first-class provisioning network segment type, enabling DPU-less provisioning scenarios. The site explorer now includes HostInband segments in its scan set and correctly tolerates a BMC interface preallocated on a HostInband segment sharing the same machine ID. The admin CLI gained a host-inband-segment mode that creates a flat VPC and HostInband segment through new RPC operations. (#1978)
- Added a `ConfigureCertificate` phase to the switch controller lifecycle, integrating with RMS job execution to automate certificate provisioning on managed switches. (#2330)
- Moved the NICo REST API database from the standalone `postgres.postgres` StatefulSet onto the shared Zalando-managed `nico-pg-cluster`, eliminating the separate REST database instance and consolidating PostgreSQL management. This is a breaking infrastructure change that requires database migration during upgrade. (#3081)
- Added support for multiple DPUDeployments in DPF, allowing BlueField-4 DPUs to be provisioned alongside BlueField-3 using separate deployment configurations with DPUs automatically routed based on hardware part number. The DPF TOML configuration structure has been updated to use a `deployments` section; existing BF3 configuration is now nested under this section and remains the default when not explicitly specified. Attempting to register a BF4 DPU when no BF4 deployment is configured fails with a clear error. (#3084)
- Added an OperationRunDispatcher to the Flow service that periodically locks, reconciles, and dispatches pending operation runs while enforcing conflict, safety, and phase policies. The dispatcher is integrated into the Flow service lifecycle for coordinated startup and shutdown. (#3093)
- Added `HostHardwareType::HpeProliantDl380aGen11` to the BMC mock, representing the first HPE hardware type supported in the test infrastructure. The mock is modeled from a real DL380a Gen11 with a BlueField-3 SuperNIC and includes authentic identity values, expected lockdown state, and iLO serial-console BIOS attributes captured from physical hardware. (#3133)
- Added NVUE REST collection for switch reboot reason and leakage sensor data. Reboot reason events are emitted as structured `reboot_reason_info` metadata, while leakage sensor readings are translated into StateSet metrics and switch health reports with `ok`, leak alert, or sensor-failure classifications. Per-path configuration flags allow independent enablement of each collection type. (#3125)
- Added a NMX-C `Subscribe` streaming collector to carbide-health that connects to eligible primary switch-host NMX-C gRPC endpoints, validates the subscribe acknowledgement, and emits received notifications as structured log events through tracing, log-file, and OTLP sinks. mTLS security support for switch host collectors is tracked separately and will be addressed in a follow-on change. (#3121)
- Added gRPC operations for querying operation runs: `GetOperationRun`, `ListOperationRuns`, and `ListOperationRunTargets`. A shared statistics collector is included to support aggregation across operation run queries. (#3146)
- Added a `bmc_ip_allocation` field to `ExpectedMachine` that gives operators explicit control over BMC IP address assignment and retention. The default `auto` behavior retains an auto-allocated address as a static reservation so it survives DHCP lease expiry, eliminating a recurring source of failures such as DPF re-registration and state machine placement issues. Additional modes include `fixed` (requires a pre-configured address), `retained` (always pins an auto-allocated address), and `dynamic` (opt-out that preserves lease-based behavior). (#2955)
- Added OpenTelemetry trace ID tagging to site-agent gRPC client response log entries, enabling operators to correlate individual RPC log lines back to the workflow that issued the call. Previously, response logs included only method, status code, and duration with no workflow context. (#3005)
- Added a VPC creation command to the admin CLI, allowing operators to define a flat VPC without modifying the configuration file and redeploying. This is particularly useful for bootstrapping environments in DPU-less deployments. (#3145)
- Added a network segment creation command to the admin CLI, allowing operators to define a host-inband network segment without modifying the configuration file and redeploying. This is particularly useful for bootstrapping DPU-less environments. (#3143)
- Added DpuFlavor configuration support for BlueField-4 DPUs in the DPF integration, extending flavor definitions to cover BF4 hardware variants alongside the existing BF3 support. (#3195)
- Updated the BMC mock to route incoming Redfish requests using the HTTP `Host` header as a fallback when the primary routing mechanism is unavailable. This improves compatibility with clients that identify the target BMC via the Host header. (#3190)
- Added the data model and protobuf foundation for an iPXE template-based operating system variant to the REST API, introducing per-OS scope options (Local, Global, Limited) alongside the existing Image and raw iPXE variants. Schema support for OS definitions to stay in sync with on-site NICo Core is included; no handler, workflow, or route wiring is activated in this change — API and SDK layers follow in subsequent changes. See https://nvidia.github.io/infra-controller/ for the updated schema. (#3160)
- Added BlueField-4 PF0 MAC address discovery via the `/redfish/v1/Chassis/BlueField_0/NetworkAdapters/BlueField_NIC_0/NetworkDeviceFunctions/0` Redfish path. The host-side base MAC is derived by applying a fixed offset of 0x10 to the value at that path, replacing the legacy discovery paths that are not valid on BF4 hardware. (#3115)
- Extended the `discover_dhcp` API to support DHCPv6, routing discovery through explicit `address_family` and `message_kind` fields. DHCPv6 stateful requests and the DHCPv6 INFORMATION-REQUEST/SLAAC observation path are now supported; existing IPv4 callers that omit both fields retain their current behavior unchanged. DPA DHCP handling remains IPv4-only. (#2988)
- Introduced `carbide-instrument`, a unified observability framework that lets NICo components declare a significant event once and emit both a structured log line and a Prometheus metric together from a single call. Metric names are validated at compile time (enforcing the `carbide_` prefix, `_total` counters, and unit-suffixed histograms), and high-cardinality values are confined to log-only context fields to keep metric series counts bounded. (#3192)
- Added a background process that periodically republishes the status of all managed hosts to the message bus. The republish interval and the set of data included are configurable, allowing operators to tune reporting frequency and payload to their environment. (#2359)
- Replaced the hand-written `/admin` configuration page with a generated configuration catalog derived from the live `CarbideConfig` and its schema. The new page covers all configuration options (previously only ~35 of ~230 were shown), displays their effective values, and indicates each value's provenance — whether it came from a config file, site overlay, environment variable, or compiled default. The catalog stays automatically in sync as new options are added. (#3223)
- Added a `carbide_log_events_total` Prometheus counter that tracks every log line emitted by a NICo binary, labeled by severity level and the component that produced it. The metric is incremented by a subscriber in the tracing stack with no changes required to existing logging call sites, making log volume and per-component error rates directly observable in Prometheus. (#3244)
- Added automatic rate, error, and latency instrumentation for every outbound gRPC call made by any NICo binary. The generated client code now wraps each method in a `carbide_instrument` helper that records a value into the `carbide_external_call_duration_milliseconds` histogram, labeled by the target service, the method name, and outcome, with no changes required to calling code. (#3245)
- Added Prometheus metrics to `carbide-dns` covering query count by type (`carbide_dns_queries_total{qtype}`), response count by result code (`carbide_dns_responses_total{rcode}`), and a request latency histogram. Existing per-request log lines are unchanged; the metrics are purely additive. (#3268)
- Added a Prometheus `/metrics` endpoint and three counters to the DPU DHCP server: `carbide_dhcp_requests_total{message_type}`, `carbide_dhcp_dropped_requests_total{reason}`, and `carbide_dhcp_leases_granted_total`. The endpoint is enabled via an optional `--metrics-listen-addr` flag served on port 10080; both the DPF DaemonSet chart and the legacy supervisor template pass this flag. Deployments without the flag continue to work unchanged. (#3286)
- Added Prometheus counters for three security-relevant events: RBAC denials (`carbide_auth_denied_total{principal_class, authorizer}`), client certificate rejections (`carbide_authn_client_cert_rejected_total{reason}`), and BMC password rotations (`carbide_bmc_credential_rotation_total{outcome}`). Each counter is paired with the existing log line for the event, making denial spikes and credential rotation failures directly alertable. (#3266)
- Improved MNNVL capability detection to cover GB300 and VeraRubin systems. Detection now checks GPU platform info and known GPU name markers first; if none match, it falls back to scanning `dmi_data.product_name` for MNNVL markers, handling cases such as VR systems where the GPU name does not carry the platform identifier but the DMI product name does. (#3300)

Added `carbide_dhcp_replies_sent_total{message_type}` to count every reply Kea sends, and extended `carbide_dhcp_dropped_requests_total{reason}` to capture eight previously uncounted hard-drop and allocation-refusal paths. Existing dashboards using the `dropped_requests` metric are unaffected: the exposed name, label key, and all pre-existing reason strings are unchanged. (#3320)
- Implemented manual control gRPCs for workflow operation runs: Pause, Resume, AdvancePhase, and Cancel. Operators can now intervene in a running operation without waiting for it to complete or fail naturally. (#3308)
- Expanded the new hardware support guide with documentation covering the upstream `libredfish` and `nv-redfish` contribution flow, live-BMC testing procedures using `bmc-explorer-cli` and `nico-admin-cli`, optional BMC mock coverage, and HCL, dependency update, and PR evidence requirements. - Added Prometheus metrics for two previously unobservable machine-stalling conditions: state-handler wake-up failures are now counted via `carbide_state_handler_wakeup_failures_total{trigger}` with a label identifying which trigger path failed, and firmware-upgrade retry exhaustion is tracked by a dedicated counter. The state-controller error count, which was previously only written to logs, is now also exported as a metric. (#3272)

When switches are discovered during site exploration but skipped because `create_switches` is `false`, an informational log message is now emitted. Operators who previously relied on the `false` default to suppress switch creation must now explicitly set `create_switches = false`. (#3280)

The new `carbide_external_call_duration_milliseconds{backend, operation, outcome}` metric provides per-backend, per-operation request rate, error rate, and latency across all three external backends. (#3333)

The `/metrics` endpoint now serves both the existing `http_*` family and the new outcome metrics in a single scrape, making every boot-path failure reason directly observable. (#3331)

Successful renewals, previously silent, are now logged at INFO level alongside the existing ERROR logging for failures. (#3326)

Added `carbide_health_otlp_export_*` counters for OTLP drain batch outcomes and instrumented health-report submission failures, making all three egress edges observable. Fanout behavior is preserved: one failing sink logs, counts, and the remaining sinks continue to receive events. (#3336)

Each deployment entry (such as `bf3` or `bf4_generic`) can now define its own `services` block to pin specific service versions or images; when omitted, the top-level `[dpf.services]` set is inherited with no behavior change for existing configurations.
